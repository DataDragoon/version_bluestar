What it is

64-bit in, 32-bit out, 8192 words deep — the mirror of Chapter 4, with three real differences

Same wrapper, same megafunction, opposite direction: 64 KiB of M10K, written by the sample packer in the AD9361 clock domain and drained 32 bits at a time by the GPIF interface. Twice the storage of the TX FIFO, because the same 8192-word depth now counts 64-bit words.

Three things genuinely differ from TX, and all three matter:

  • The occupancy counters have different widths — 13 bits on the write side, 14 on the read side. Same physical buffer, counted in different units.
  • The full flags are actually read. Both sides consult them, and both concatenate full & usedw to work around the counters' inability to express “completely full”.
  • The clear line is different. TX is cleared only by a global reset; RX is flushed every time the host disables RX.

The occupancy it makes decisions on is therefore at least two cycles stale, on top of the five-stage pointer synchronizer — which is why the watermarks reserve a whole DMA buffer of margin.

The two waterlines

both derive from rdusedw, and they do different jobs

1

rx_fifo_enough — may a transfer start?

Compares rdfull & rdusedw — a 15-bit value — against the GPIF buffer size. It trips once 2048 32-bit words (8 KiB, one whole DMA buffer) are readable on SuperSpeed, 1024 on High Speed.

It is one of four AND terms in can_rx. False means the state machine never leaves IDLE toward a read: no rdreq, no DMA acknowledge, nothing sent to the host. In packet mode this sample count is replaced entirely by “a packet header exists”.

2

rx_fifo_critical — is RX about to overflow?

Compares bare rdusedw (no full flag) against half the read-side capacity minus one buffer — tripping at 6144 words on SuperSpeed.

This is the signal that reaches back into bus arbitration, and it is the reason Chapter 2's half-duplex bus behaves the way it does. Normally TX is checked first, deliberately, to avoid discontinuities in the transmitted signal. But a critical RX is checked before both — so a nearly-full RX FIFO pre-empts a pending TX transfer. It is the anti-overflow escape hatch.

The comment and the arithmetic disagree

The source calls this “can we not fit one more block of data in RX buffer?”, but the expression measures against half the read-side depth. The read side holds 16384 words, so “critical” actually fires at 37.5% full, not one block from full. The TX equivalent has no such halving. Conservative rather than wrong — but if you are reasoning about headroom, use the number, not the comment.

The clear line, and a crossing that is waived rather than synchronized

worth knowing if you ever chase an intermittent RX fault

Unlike TX, the RX FIFO is flushed on every RX disable. The chain is short:

FX3 asserts CTL[4]  (dma_rx_enable)
  → sampled by a single flop in fx3_gpif → rx_enable_pclk
  → inverted, straight into aclr — no synchronizer

rx_enable_pclk lives in the PCLK domain, which is the FIFO's read clock. Its assertion edge is therefore synchronous to the read side but fully asynchronous to the write side, where the sample clock runs. There is no RTL synchronizer on that path. De-assertion is handled inside the megafunction; the assertion edge is covered by explicit timing waivers instead:

set_false_path -from {fx3_gpif*rx_enable} -to {*rx_fifo*:wraclr|*}

By contrast the enable that gates the writer is properly three-flop synchronized before use. So: the writer's enable crosses safely; the FIFO's async clear crosses by constraint waiver. Both are defensible, but they are not the same mechanism, and only one of them is visible in the RTL.

The sibling FIFOs

two more, sharing the same control structure

rx_meta_fifo — 128 in, 32 out, 2048 deep

Carries the timestamp headers alongside the samples. Cleared by the same NOT rx_enable_pclk line, deliberately, so metadata and samples can never desynchronize. Its header is built as a 128-bit word and read out as four 32-bit slices; the last slice has its low 16 bits overwritten on the way out with the TX underrun flags.

Only one of its flags does any work: the read-side rdempty, which gates rx_meta_ok in the transfer-start decision. Its rdfull and read-side occupancy are declared in fx3_gpif and never referenced — and note the port is spelled usedr, not usedw, unlike every sibling.

A misleading comment

The depth constant is annotated “2048 -- 32-bit words”. It is not. LPM_NUMWORDS is a write-side count, so it is 2048 × 128-bit entries = 8192 32-bit words. The firmware reads it correctly; the comment does not.

lb_fifo — 64 in, 64 out, 512 deep

The digital loopback path, and the only one of the three that runs TX → RX: written in the TX domain from the words popped off the TX FIFO, read in the RX domain. Because both widths are equal it elaborates a plain dcfifo rather than the mixed-width variant.

Its write-full flag is the one piece of genuine back-pressure in the system: it reaches back into tx.vhd and stalls the TX reader for three cycles so loopback data is not dropped. Its read side is pulled only when the previous word is fully unpacked and the RX sample FIFO has room.

Curiously, both its clocks alias the same net on this board, so it is physically synchronous while being parameterized asynchronous — costing latency and gray-code logic to keep the wrapper uniform. It is also the only one of the three whose clear is properly resynchronized in RTL, which is just as well: it is the one the timing waivers do not cover.

Where the data comes from

one 64-bit word, tracked

Before it arrives:

AD9361 → LVDS pins → axi_ad9361 (deserialize)
  → adc_assignment_proc (to generic sample streams)
  → rx_mux (select ADC / counter / loopback, apply trigger)
  → fifo_writer (pack into 64 bits) → rx_fifo

After it leaves, split into two 32-bit halves:

rx_fifo → CDC to fx3_pclk → fx3_gpif.gpif_mux
  → register_gpif (tristate) → fx3_gpif[31:0] pins
  → FX3 GPIF II → USB 3.0 → libbladeRF → your driver

If metadata is on, four header dwords are emitted ahead of the samples in the same transfer, and the last of them carries the TX underrun flag. That is the only channel by which a transmit-side problem reaches the host — which is why an RX stream has to be running to observe one.
