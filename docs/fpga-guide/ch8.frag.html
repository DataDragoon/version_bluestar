Two planes that never touch

the whole machine on one page · control above, samples below

Seven chapters of detail resolve into a simpler claim than the parts suggest. The board is two independent planes that share a package and almost nothing else:

  • A control plane — host command packets to the NIOS, over the Avalon bus, out through SPI and GPIO to the AD9361's registers. It decides frequency, gain, bandwidth, mode. It never touches a sample.
  • A data plane — IQ samples over the GPIF bus, through FIFOs, through the reader and writer, across LVDS to the converters. It carries everything and understands nothing. No CPU is involved at any point.

They meet in exactly two places: inside the FX3, which multiplexes both onto one USB cable using different endpoints, and inside the AD9361, where a register written by the control plane changes what the data plane receives. Nowhere in the FPGA do they share a wire.

The control plane, end to end

what happens between your Python call and the LO moving

Every configuration change on this board is software writing registers one transaction at a time. There is no hardware sequencer — the FPGA contributes only the timestamp compare that says when, and the pins that carry the bits.

The retune is not the expensive part

Stage 9 — the actual frequency change — is 1.8 µs. Stages 2 and 10 are 250 µs each. Better than 99% of a retune's wall-clock cost is USB transport, not RF settling, which is why the scheduled-retune path exists at all: it moves the decision onto the FPGA so the transport cost is paid once, ahead of time, instead of once per step.

Two structural facts that bite

Deferred work is starved by packet traffic. The NIOS main loop only calls do_work() on iterations with no pending packet. RFIC writes are enqueued there, not executed inline — so a host that hammers the command UART back to back stops the retune queue advancing at all. This is why libbladeRF sleeps 100 µs between RFIC status polls: the sleep is what lets the NIOS reach its own queue.

The CPU is never reset. reset_reset_n is tied high in the VHDL, so every bit of state — register shadows, retune queues, the fastlock profile table, the 256-profile counter — survives bladerf_open, bladerf_close and USB re-enumeration. Only reconfiguring the FPGA clears it.

The data plane, end to end

the same trip for a sample, and the four places it can be silently lost

The two directions are near mirror images and share exactly one resource: the 32-bit GPIF bus, which is bidirectional and therefore half-duplex. Everything else is duplicated.

Note the asymmetry in where flow control sits. TX is guarded at the host end — fx3_gpif refuses to start a transfer above 6144 words, and fifo_reader has no watermark at all. RX is guarded at the radio end — fifo_writer carries the credit check itself. That follows from how each direction fails: TX fails by running dry, which only the side holding the host buffers can prevent; RX fails by overrunning, which no upstream can prevent because the ADC does not stop.

Four silent failures, collected

An idle TX keeps radiating
ch 06
On underrun data_v goes low, the DAC register's clock enable is data_v, and the FIFO output holds its last word — so the DAC parks on the last sample and emits an unmodulated carrier at the LO. Not silence. libbladeRF requires the last two samples of a burst be zero.
Samples outside ±2047 wrap
ch 06
unpack() reads only bits 11:0 of each lane and re-derives sign from bit 11. Nothing clips, nothing warns.
RX overflow has no status bit
ch 07
The overflow counter is mapped to open and synthesized away. The LED is the only fabric-level indication — and its one-shot reloads in an elsif, so it stays dark for the duration of the event. The host can only infer an overrun from a timestamp discontinuity, which requires metadata.
A late TX buffer is discarded whole
ch 04
If the header timestamp has already passed at DMA time, fx3_gpif diverts to SAMPLE_WRITE_IGNORE and drops all 2048 words. The underrun flag it raises rides back in an RX header — so you need an RX stream running to see a TX fault.

What this adds up to for a stepped-frequency sweep

The control plane costs ~500 µs per retune, almost all of it USB, against 1.8 µs of actual RF settling. The data plane will not tell you when it has failed. Both point the same way: keep the streams running continuously and move the per-step decisions onto the FPGA, which is what the scheduled-retune path is for — and which needs the SC16_Q11_META format and the TX-side HDL patch that this build does not yet have.
