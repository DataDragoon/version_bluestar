What it is

the TX sample reader · between the TX FIFO and the DAC

Chapter 4 covered the TX FIFO as storage. fifo_reader is what decides when to pop it and what to do with the word. It unpacks 64-bit words into per-channel samples, holds a burst until its scheduled timestamp arrives, and hands the result to the DAC.

Like its RX counterpart it runs in the tx_clock domain and contains two state machines — but here the coupling is a licence rather than an interlock: the metadata machine decides whether the sample machine may read at all.

One input is not what its name suggests: fifo_empty is the trigger-gated empty from Chapter 4, not the FIFO's raw flag. Everything below inherits that — including, as it turns out, the underflow detector.

A second one is misread even more often. fifo_holdoff, the reader's only back-pressure input, has nothing to do with the TX FIFO: it comes from the loopback FIFO's full flag, and tx.vhd stretches it by three cycles so the loopback path has time to drain. The TX FIFO itself can never push back on this module.

781 lines of VHDL, instantiated exactly once — U_fifo_reader in tx.vhd. It and fifo_writer (Chapter 7) read as a matched pair: same package imports, same current/future record idiom, same split into a synchronous process that does nothing but current <= future and a process(all) that does all the work. The symmetry ends at the first decision that costs something.

Two state machines, one licence

the meta FSM decides when; the sample FSM decides what

The first two sample states are one cycle each and exist only to recompute the channel packing. They are re-entered every time the FIFO runs dry — which has a side effect worth knowing: a MIMO channel enable change made while the FIFO stays fed is never noticed. The configuration is only re-sampled after an underrun.

The counters balance exactly. The meta FSM loads dma_buf_size − 4 = 2044 on SuperSpeed — the 2048-word DMA buffer less its four header words — each read subtracts NUM_STREAMS, and it exits at ≤ 2, giving 1022 reads per message. That is precisely the 2044 words the GPIF wrote on the other side.

The threshold is not 0 because of turnaround, and the source says so in as many words: “Look for 2 because of the 2 cycles passing through META_LOAD and META_WAIT after this.”

What one read serves

the cadence, and what gets thrown away

A single 64-bit word can satisfy more than one request. The governing quantity is samples_left_init = NUM_STREAMS − enabled_channels:

ModeChannelsRequests per FIFO read
SC16_Q1121
SC16_Q1112
8-bit22
8-bit14
packed 12-bit24 requests per 3 reads

The packed mode is the interesting one: it keeps a 48-bit carry buffer and reassembles samples that straddle word boundaries, so three 64-bit words yield eight 12-bit IQ pairs with nothing wasted. On the fourth cycle it reads nothing at all — everything comes from the buffer.

Its entry condition carries a guard the writer's packer does not:

if (highly_packed_mode_en = '1' and NUM_STREAMS = 2) then
    unpack_sc12q11( ... );

fifo_writer packs SC12Q11 whenever the mode bit is set, whatever NUM_STREAMS is. On this board the generic is 2, so the two agree and nothing is wrong in the shipped image. On a single-stream instantiation of the same source they would disagree, and the writer would emit a format the reader would not parse.

The standard unpack throws away a quarter of the word

The bit positions are hardcoded constants that the source itself flags as provisional:

constant I_HIGH : natural := 11;   constant I_LOW : natural := 0;
constant Q_HIGH : natural := 27;   constant Q_LOW : natural := 16;
-- The following 4 constants are platform-specific and perhaps
-- should be parameters instead. This is good enough for now.
OutputBits takenBits discarded
ch0 I / Q11:0 / 27:1615:12, 31:28
ch1 I / Q43:32 / 59:4847:44, 63:60

Those discarded nibbles are the host's sign extension — the FPGA re-derives sign from bit 11 instead. Which means a host sample outside ±2047 is silently truncated here, not clipped. It wraps.

The unpacker sign-extends bit 11 back up to 16 bits, and then two stages later dac_assignment_proc keeps 11:0 again and left-justifies into the DAC — so the sign extension it performs is discarded before it reaches the AD9361. Note also that this is not the inverse of what the writer does: pack() stores both 16-bit halves of every sample whole, and the RX direction really does carry all sixteen bits. The transmit path is twelve bits wide, twice; the receive path is not.

The timestamp gate

why the comparison subtracts one

The header's 64-bit timestamp is read, one is subtracted, and the result is what META_WAIT compares against the live TX counter. That subtraction does two unrelated jobs at once, which is why it looks arbitrary.

1

It pays for the pipeline

The go signal is registered, the sample FSM samples it a cycle later, and the output is registered again. Firing the comparison one tick early lands the first sample on the DAC at the requested timestamp rather than one clock past it.

2

It encodes “transmit now”

The host signals immediate transmit by writing timestamp zero. Under the subtraction that wraps to all ones — which the FSM recognises as its NOW constant.

This needs an explicit exception, and there is one. The look-ahead rule is “a future timestamp means don't go yet”, and all-ones compares greater than every real counter value — so without the carve-out an immediate burst would never start. The condition reads “in the future and not the NOW sentinel”. Both halves are visible in four lines:

meta_time := unsigned(meta_current.meta_fifo_data(95 downto 32)) - 1;
...
if( (timestamp >= meta_current.meta_p_time or
     meta_current.meta_p_time = MAX_TIMESTAMP) and ... ) then
    meta_future.meta_time_go <= '1';

Which is worth stating plainly, because Chapter 2 describes the same mechanism from the host's side: there is no TX_NOW flag anywhere in this module. There is an underflowed subtraction and a constant that recognises the result. The flags word of the header is never read by any RTL at all.

One thing the source cannot settle

The go signal is not default-cleared, so it stays asserted through the first cycle after the message ends, and the sample FSM watches the read strobe one cycle late. The ≤ 2 exit threshold is the author's slack for that turnaround — the comment says so.

Whether a request landing in that one-or-two-cycle window can pull an extra, uncounted word, and whether the margin cancels the lag exactly or over-shoots by one word per message, is not answerable by reading the RTL. There is no explicit interlock preventing it. It would need a simulation with a realistic request cadence.

Idle does not mean silent

the finding that matters most for a stepped sweep

Chapter 4 noted that the DAC holds its last value when the FIFO runs dry. Here is the actual mechanism, in three links:

  • The valid strobe clears itself. Every unpack function writes data_v := '0', and the unpack result is assigned as a whole record outside the case statement — so in every state, every cycle, data_v starts low. It is re-asserted in exactly one line, inside READ_SAMPLES, inside the not-empty branch.
  • The sample data does not clear. Nothing zeroes it. The FIFO is show-ahead, so with no read its output simply holds the last word, and the reader keeps re-unpacking that same stale word forever.
  • The consumer is clock-enabled by the strobe. The DAC register's enable is data_v. Low means never reloaded, so it retains its last value and hands that constant to the AD9361.

Put together: on underrun, or after TX is disabled, the DAC is parked at whatever IQ value was last valid. That is not silence — it is a DC offset into the mixer, which radiates as an unmodulated carrier at the LO, at that sample's amplitude and phase.

There is no TX mux, no zero-injection and no squelch anywhere in the hosted image. libbladeRF treats this as the caller's problem and documents the obligation: the last two samples of a burst must be zero. Two, not one, because one 64-bit word carries two samples and which one gets frozen depends on where the unpacker stopped.

Why this matters between sweep steps

If the TX stream is ever allowed to run dry between frequency steps, TX1 and TX2 keep radiating the last sample rather than going quiet. For a stepped-frequency sweep that is a CW tone sitting at the previous step's LO for the whole gap.

Wired but unread

and one detector that is always firing

The underflow detector has no request term
note
The condition is “TX enabled, FIFO dry, and licensed to transmit” — it does not require the DAC to have asked for a sample. So with TX enabled and the host not streaming, it asserts every single clock. That is the origin of the underflow LED being lit whenever TX is idle. An armed-but-unfired trigger does the same thing, since the empty flag it watches is the trigger-gated one.
underflow_count → open

A 64-bit counter with edge detection, built and then left unconnected. Exactly as on the RX side. Only an LED escapes the module, and only while the NIOS has not taken manual control of the LEDs.
The host never sees this underflow

The UNDERRUN flag the host actually receives comes from somewhere else entirely — the GPIF raising it when a message's timestamp has already passed at DMA time. fifo_reader's own detection reaches a front-panel LED and nothing more.

The throttle generic is 0, which makes the entry condition compile-time false and the state's own counter range collapse to a single value. An entire state, doubly dead.
Both occupancy inputs unread
dead
The sample and metadata FIFO fill levels are wired in from live signals and never referenced in the body. The reader is driven purely by empty flags. Both synthesize away.
The whole packet path dangles
dead
Its outputs are connected at the top level and consumed by nothing; the ready input is tied high, making four tests statically true. The packet state is reachable at runtime but everything it produces is discarded — the port exists for other platform variants.

Both sit unread in the cached header and stay at zero forever. The TX packet path cannot address a specific core even where it is used.

A synthesis don't-care, not a zero. Harmless, since it is written before it is read — but it means simulation and hardware need not agree on the first cycle after reset. fifo_writer has two fields of its own like this.

The LED one-shot, and why the RX one behaves differently

The reload is a separate statement here, not an elsif:

underflow_led <= '0';
if( downcount /= 0 ) then
    downcount := downcount - 1;
    underflow_led <= '1';
end if;
if( underflow_detected = '1' ) then
    downcount := to_integer(underflow_duration);
end if;

So the decrement still runs while the condition is asserting, and a sustained TX underflow lights its LED and holds it. Chapter 7 shows the writer's version of these same three processes with the reload as an elsif instead — one keyword apart, opposite behaviour, and the RX LED stays dark for the whole event.

Two things a simulator would flag

The channel index arithmetic can compute an out-of-range value — it is saved only by an enable guard on the same line. Relax that guard and it breaks.

And the cadence formula happens to be correct only because there are exactly two streams. A four-stream instance with two enabled would compute three requests per read instead of two. Harmless here; latent everywhere else.

Two more sit inside unpack_sc12q11, both inert at this instantiation. The procedure declares data as a parameter and uses it throughout — except in its cycle = 2 branch, which reaches past the parameter list and reads the signal fifo_data directly; here they are the same signal, so it works. In the cycle = 3 branch, rv(1)'s fields are resized using rv(0).data_i'length; both are 16, so it works. The reader also declares packed_cycle over 0 to 4 while only using 0 through 3. All three are real, all three are harmless, and all three would bite the first time this module is reused with different parameters.
